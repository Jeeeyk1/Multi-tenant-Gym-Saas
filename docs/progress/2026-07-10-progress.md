## Billing Phase 3 — lead capture (landing → admin queue → convert)

**DB**: `signup_requests` (migration `0040`). `planInterest` is free text, not a FK — the
landing page's `SaasPlan` (marketing pricing cards) and the internal `Plan` (what `Subscription.
planId` actually points to) are two different tables with two different price lists in this
codebase. A public lead form has no business resolving one to the other; the admin picks the
real `Plan` during Convert, same as any other provisioning.

**New `leads` API module**: public `POST /public/signup-requests` (rate-limited 5/hour/IP),
admin list/get/update-status/convert. **Convert doesn't re-implement provisioning** — it reuses
the existing `POST /admin/gyms` flow (pre-filled from the lead) and just links the resulting
gym id, closing the loop. Refactored `RateLimiterService` out of `ai-insights` into
`common/rate-limiter/` since it's now shared by two unrelated features — meets CLAUDE.md's bar
for `common/` (generic, stable, reusable) that it didn't meet as a single-module private helper.

**Admin app**: `/dashboard/leads` queue; `/dashboard/gyms/new?leadId=` prefills the provisioning
form and auto-converts on success. **Landing app**: pricing-card CTA now opens a `SubscribeModal`
lead form instead of a `mailto:` link, posting straight to the public endpoint.

### Bug found and fixed by a live smoke test

Booted the API against real Postgres/Redis and ran the full loop by hand (curl, minted JWTs
directly since there's no seeded admin password) for the first time since Phase 1 shipped —
**gym provisioning 500'd on every request.** `subscriptions_status_check` and
`invoices_status_check` (defined in `0008_plans_subscriptions`, long before the billing rework)
never got updated when Phase 1 introduced `PENDING_PAYMENT`/`SUSPENDED` and `AWAITING_
VERIFICATION`/`REJECTED` — the DB was silently rejecting the very statuses the new code writes.
Invisible to unit tests (mocked Prisma never hits a real constraint). Fixed in migration `0041`.

Re-ran the full loop live after the fix and it worked end to end: submit lead → mark contacted →
provision (with the lead prefilled) → convert → confirmed 402 on the locked gym → owner submits
payment reference → shows up in admin's pending-payments queue → admin verifies → invoice PAID,
subscription ACTIVE, gym unlocks (402 → 200). All test rows cleaned up afterward.

**Verified:** typecheck clean on api/web/admin/landing/mobile. 274/274 API tests pass (10 new:
leads use-cases + rate-limit behavior). Live smoke test as described above.
