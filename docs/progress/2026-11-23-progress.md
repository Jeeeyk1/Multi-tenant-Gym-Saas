# Progress — 2026-11-23

## Member fitness plan, phase 1 (API) — DONE

First step of the member-app rebuild: goal → deterministic daily targets → daily progress. This
phase is the API. Onboarding (phase 2) and the dashboard (phase 3) build on it.

### What was built
- **Calculator** (`modules/fitness-plan/domain/fitness-plan.calculator.ts`): pure functions, no AI.
  - Mifflin–St Jeor BMR × activity factor = TDEE.
  - Three paces per direction:
    - **Loss:** 0.25 / 0.5 / 0.75 kg per week, capped at 1% of bodyweight.
    - **Gain:** +150 / +250 / +400 kcal.
  - Calorie floor is max(BMR, 1200 F / 1500 M / 1350 unspecified), rounded up.
  - Macros:
    - protein 1.8 g/kg on loss, 1.6 otherwise, using the BMI-25 weight when BMI ≥ 30;
    - fat 25% of calories, minimum 0.6 g/kg;
    - carbs are the remainder.
  - Water: 35 ml/kg.
  - Goal date counted from the gym's local "today".
  - `CALCULATOR_VERSION` is stored with every plan.
- **Safety rules:**
  - Weight loss is refused when BMI < 18.5, when the target is below BMI 18.5, or when there is no target.
  - A health caution (pregnancy or a medical condition) turns weight loss into maintenance.
  - Under 18 or health caution: only the gentlest pace.
  - A pace that the floor or cap makes no faster than the previous one is shown as unavailable.
- **Endpoints** (member-only, new `MemberSelfGuard`):
  - `GET …/fitness-plan/options`
  - `POST …/fitness-plan`
  - `GET …/fitness-plan`
  - `GET …/fitness-plan/daily-nutrition?date=`
- **Profile:**
  - New `sex`, `unitSystem`, `healthCaution`, `healthDataConsent` fields.
  - `activityLevel` is now SEDENTARY / LIGHT / MODERATE / VERY_ACTIVE / ATHLETE (existing rows mapped).
- **Food logs:** `GET …/food-logs` takes `date` (gym-local day) and `limit` capped at 100.
- **Meal plan:**
  - The muscle-gain goal is now recognised.
  - The diet type is passed as a strict rule.
  - The saved plan's targets are used when the request gives none.
  - The member's name is no longer sent to the AI provider.

### Bugs fixed
- `PATCH me/profile` silently dropped six onboarding answers: target weight, days/week, experience,
  style, diet and injuries. Only six of the twelve fields were mapped.
- The meal prompt compared the goal with `GAIN_MUSCLE`, but the enum value is `BUILD_MUSCLE`. Diet type was never sent.

### Decisions
- **No AI for the targets:** formulas are free, instant, repeatable and explainable.
- **Health data is the member's own:**
  - Plans need explicit consent. Withdrawing consent deletes saved plans in the same transaction.
  - Staff profile reads omit `healthCaution` and consent.
  - Staff edits can't set sex, units or health fields.
  - Fitness-plan routes refuse staff, because pace availability would reveal the health flag.
- **Plan history is kept:** daily nutrition for a past date uses the plan active that day.
- **One source for input ranges:** `PROFILE_LIMITS` is used by the calculator and the DTO, and mirrored by
  migration 0046's CHECK constraints.

## Member onboarding rebuild, phase 2 (mobile) — DONE

`app/onboarding.tsx` was rewritten as an 11-step conversational flow. The coach "types" each question
in chat bubbles, then the answer controls appear.

### Flow
1. **Welcome:** the coach drops in and floats over pulsing rings in the gym's colour, while the greeting types underneath.
2. **Health-data consent:**
   - What is collected and why.
   - Staff can't see it, and withdrawing it deletes the plan.
   - "Not now" finishes onboarding without a plan.
3. **Goal**, then **sex** (formula only), then **body**:
   - kg·cm / lb·ft toggle; values already typed are converted.
   - Client-side range checks mirror the API's `PROFILE_LIMITS`.
4. **Goal weight:**
   - Required for lose and gain goals.
   - Instant hint when it contradicts the goal.
5. **Activity:** five levels, each with examples.
6. **Training:** days per week plus experience.
7. **Diet:** diet type, optional injuries, and the "pregnant or a medical condition" checkbox.
8. **Plan:**
   - One PATCH saves every answer with consent, then `GET /fitness-plan/options`.
   - Pace cards show goal date, weekly change in the member's unit and daily calories.
   - FAST is red ("Needs strict consistency").
   - Unavailable paces show why.
   - A maintenance card appears for goals without a direction, plus a "check with a doctor" notice when advised.
   - API errors offer "Fix my answers", which jumps to the step that caused them.
9. **Reveal:**
   - Calories and macros count up.
   - "YOU'RE IN" stamp with a success haptic.
   - Goal date shown.
   - Finishing sets `onboardingDone` and opens the dashboard.

### Design
- Clean, card-based look on the existing theme tokens. Accents use the gym's configurable `theme.primary`;
  FAST and errors use the status red.
- Ionicons replace all emoji.
- **Reduce motion respected:** no typing animation, no count-up, and the video is paused on its first frame.
- New components live in `components/onboarding/`:
  - `CoachMessage`, `CoachMascot`, `WelcomeStage`;
  - `controls` (OptionList, SegmentedToggle, NumberField, PrimaryButton, Notice);
  - `PaceCards`, `TargetsReveal`, `format`, `use-reduce-motion`.

### Notes
- **Mascot:** the waving pose is cut out of the first frame of `mascot-greeting.mp4` with its background removed
  (`assets/mascot/coach-wave.png`), then animated in code.
  - **Idle:** float and sway.
  - **Talking:** hops while a message types.
  - **Tap:** jump with a haptic.
  - **Entrance:** bounce in.
  - It also replaces the gym logo that the chat avatar was showing. The video itself is not shipped and `expo-video` was removed.
  - A proper pose set (Lottie or Rive) from an illustrator would replace this.
- **Tenant branding fix:** the gym's colours and logo were only saved when a gym code was entered, never
  refreshed after login or cleared on sign-out. A phone could show another gym's logo.
  - `AuthContext` now loads branding and the gym name from `GET /gyms/:gymId/detail` on login and session restore.
  - Sign-out clears it.
  - The token carries neither the gym name nor the gym code, so the welcome had said "Welcome to the gym".
- There is no backend badge for finishing onboarding yet; the "YOU'RE IN" stamp is visual only.
- **Review fixes:**
  - `targetWeightKg` and `injuries` accept `null` on PATCH profile, so a saved goal weight can be cleared.
    Before this, an old target could create a weight-loss plan after switching to "Get fit".
  - A failed recalculation no longer shows stale pace cards.
  - "Continue without a plan" appears when no pace is safe.
  - Late branding responses for a previous session are ignored.
  - Saving a plan no longer refetches the options.
  - Feet and inches fields have spoken labels.
  - With a screen reader on, content appears immediately and each question is announced.
  - "Not now" shows an error instead of navigating when the save fails.

## Member dashboard, phase 3 — DONE (API + mobile)

### Built
- **Weigh-ins:** `POST …/fitness-plan/weigh-ins` (member-only).
  - Logs the weight and updates the profile weight in one transaction.
  - When weight has moved ≥ 2 kg since the active plan, the plan is recalculated at the same pace.
  - Reports `goalReached`, counting within 0.5 kg as reached.
- **Weight history:** `GET …/weight-logs` now lets members read their own history. Before, it required
  `members.view` even for the member themself.
- **Per-member monthly AI limits** (`ai/domain/member-ai-limits.ts`, `MemberAiLimitsService`):
  - Limits per month: workout plan 4, exercise swap 30, instructions 60, meal suggestion 30, meal photo 20, typed meal 60.
  - `GET …/ai/usage` reports what's left. Limits reset at the gym's local month start.
  - **Enforcement:** a usage row is reserved inside a transaction under a per-member, per-feature advisory lock,
    then filled with tokens as soon as the provider answers, before parsing. Concurrent requests can't
    overshoot, and replies that fail to parse still count. A failed provider call releases the reservation.
- **`AiFeature` enum:** replaces the raw feature-key strings. Meal analysis is split into `analyse_meal_photo`
  and `analyse_meal_text`.
- **Meal idea:** a single-meal suggestion without explicit targets aims at today's remaining calories and
  protein, between 200 kcal / 15 g and 40% of the day.
- **Migration 0047:**
  - index `ai_usage_log (user_id, used_at)`;
  - `tokens_used` CHECK relaxed to `>= 0` (reservation rows, and providers that report 0).

## Fix — AI meal suggestions failing (400 and 500)

- **400:** `GenerateMealPlanDto.targetCalories` had `@Min(800)`, a full-day floor, so every single-meal request
  with its own calorie target (e.g. 600) was rejected.
  - The DTO minimum is now 100.
  - The use case rejects a FULL_DAY target under 800 with `TARGET_CALORIES_TOO_LOW` (422).
- **500:** Groq `gpt-oss-120b` reasons before answering, and reasoning tokens count against `max_tokens`.
  - On the real meal prompt it used 1,498 of 1,500 tokens reasoning and returned empty content, which crashed JSON extraction.
  - `GroqProvider` now sends `reasoning_effort` (new `AI_REASONING_EFFORT`, default `low`) for gpt-oss models.
    That roughly halves tokens and latency.
- **Bad AI replies:** a shared `parseAiJson` turns empty, cut-off or non-JSON replies into `AiResponseError`
  (502 `AI_BAD_RESPONSE`, retryable) in all five member AI use cases. Meal analysis also rejects replies with
  missing numbers.
- **Mobile AI Coach:** shows the API's error message instead of a generic alert, and rounds photo-meal values to the
  API's precision before saving (same 400 risk as the Nutrition screen).
- **Verified live:**
  - single meal with no target → ~900 kcal;
  - 600 kcal single meal → OK;
  - full day → 3 meals, ~2,240 kcal;
  - full day 600 → 422.
- **426 tests pass.**
