## Phase 4C — AI cost controls, part 3: confirm assistant actions (branch `feat/ai-action-confirm`)

### Done
- **Server-side confirmation.** Before, the assistant ran register, renew, suspend and reactivate as soon as the
  model called them, and the only safeguard was a line in the prompt. Now the model can only propose:
  - `ActionTools.propose` checks the input, the person's permission and that the member or plan is in this gym, and
    writes a plain summary (e.g. "Suspend Juan Cruz (MBR-0001)…").
  - `PendingActionStore` keeps it in Redis for 10 minutes. The key includes the gym and the person, and `GETDEL` makes
    it single use.
  - The answer ends there with a fixed line ("Nothing changes until you confirm"), so the model can't claim it
    already happened.
  - `POST …/insights/actions/:id/confirm` runs it through the existing use cases (they check permissions again).
    `…/cancel` drops it. Neither calls the AI.
  - One action per answer. Invalid proposals are fed back to the model so it can ask the user.
- **`ToolRegistry`** now has only the read tools. Action tools are in `ActionTools`, their names in the
  `AssistantAction` enum. The input helpers moved to `tool-input.ts`.
- **Web and mobile:** an action card under the answer with the summary, the confirm button (e.g. "Suspend") and
  Cancel. After confirming, the result appears as a chat message. The card's outcome is sent back in the chat
  history, so the assistant knows what happened.
- **Docs:** API reference (`pendingAction`, confirm, cancel) and `ai-usage.md`.

### Decisions
- Redis rather than a table: proposals are short-lived and the logs record each step. The store fails closed (not the
  fail-open `CacheService`).
- The confirm needs only `insights.query` plus the action's own permission, checked by the use case. Someone else's
  action id returns 404, the same as an expired one.

### Review fixes (before commit)
- **Amount paid** follows the renew endpoint's rules (more than zero, 2 decimals), with a ₱1,000,000 ceiling.
- **Sure-to-fail proposals** are refused up front instead of failing on confirm: already suspended, already active,
  or renewing a member who has no plan without naming one.
- **Ids** must be UUIDs, with a friendly hint (e.g. a membership number instead of the member id).
- **Unexpected errors** while proposing (e.g. the database) are logged and not shown to the model. Input and
  permission problems (`ToolInputError`, domain errors) still are.
- **Clients:** a fast double tap can't send two confirms, and a card past its 10 minutes shows "expired" instead of a
  button that can only fail.
- **Tests added:** `PendingActionStore` (key per gym and person, TTL, GETDEL), `CancelActionUseCase`, and the
  amount and state rules.

### Verification
- 566 API tests pass. The API, web and mobile typechecks pass. Lint shows no new warnings.

## Phase 4D — store requirements, part 2: chat safety API (branch `feat/chat-safety`, stacked on #28)

Apple guideline 1.2 (user-generated content) requires reporting, blocking and acting on reports.

### Done
- **Migration `0055_chat_safety`:** `message_reports` (one per person per message, a reason enum, OPEN, DISMISSED or
  REMOVED, and the reviewer), `user_blocks` (one-way, unique, can't block yourself), and
  `users.community_rules_version`.
- **Community rules** (`domain/community-rules.ts`, version 1): `GET` and `POST …/chat/rules/accept`. Members must
  accept before posting in community chat; staff aren't asked.
- **Report** (`POST …/chat/messages/:id/report`): anyone who can see the message can report it, but not their own.
  Reporting again is a no-op. Each new report is logged at `warn`.
- **Block** (`GET/POST/DELETE …/chat/blocks`): only people in this gym can be blocked. Their messages are left out of
  the blocker's history, and live messages skip the blocker's sockets (the per-person room from 4D-1, with
  `.except()`).
- **Moderation queue** (`chat.manage`): open reports grouped by message, then dismiss or remove. Removing soft-deletes
  the message and sends `message.deleted` to open chats through `ChatSessionsService`.
- **Docs:** `community-chat.md` (Safety section and error codes) and the API reference.

### Decisions
- Blocks are FitOps-wide, not per gym: a person blocked at one gym stays blocked if both join another.
- Only members must accept the rules. Staff run the chat and post announcements.
- The rules text lives in the API, so mobile and web show the same version.

### Review fixes (before commit)
- **Rollout:** enforcing the rules would have stopped every member on the current apps from posting, with no error
  shown. It now sits behind `COMMUNITY_RULES_ENFORCED` (off by default, `CommunityRulesPolicy`). Turn it on once the
  app builds that show the rules are live. `GET …/rules` returns `required`.
- **Reply previews** quoting a blocked person are hidden in the history. Live quotes and reactions are hidden by the
  apps.
- **The queue** is grouped and paged in SQL, so report counts are complete and older reports stay reachable.
  Response: `{ data, meta }`.
- **Remove** is one transaction (reports and message together), announced after the commit.
- **The gateway** still acks a saved message if the blockers lookup fails (no duplicate resends).
- **`ReportAction` is an enum.** Unblock keeps a loose id check because seed ids aren't version-4 UUIDs.
- **Tests added:** list-messages (exclusion and reply redaction), the gateway's `.except`, staff who are also members,
  the switch off, the transactional remove, and the paged queue.
